# Gen 6 Random Battles: local RL assessment

**Update (September 12): the playable learner is now implemented.** See [README.md](README.md) for play, training, evaluation, and current limitations. The text below preserves the initial assessment; its statements that no learner exists and the arena tests fail describe the workspace before implementation.

Assessed September 11, 2026. **A small structured policy/value agent is practical on this laptop. The existing arena is not ready for learner integration.** This change begins with a reproducible, isolated simulator benchmark; it does not implement or train a learner.

## Workspace findings and scope

- Installed stack: Node 24.19.0, TypeScript 5.9.3, pinned `pokemon-showdown@0.11.11`; Python 3.14.7. Torch, NumPy, Gymnasium, and poke-env are absent from the active Python environment.
- Existing arena already runs in-process `BattleStream`, redacts player observations through `getPlayerStreams`, seeds teams separately, launches Python agents, and records audits. Reuse these concepts. Do not put SQLite writes, full audit retention, or a new Python process per game in the training hot path.
- `src/contracts.ts` fixes the arena to `gen9randombattle` and permits only Terastallization as a move modifier. Merely changing the format string would leave Gen 6 Mega Evolution unsupported and mix assumptions across the UI, audit verifier, records, and agents.
- `agents/runner.py` implements random choice and a first-available-move policy. The latter does **not** implement the strong/accurate-attack heuristic advertised by `agents.json`. No observation encoder, model, optimizer, rollout buffer, or learner checkpoint exists.
- `npm run typecheck` passes. Before changes, `npm test` passed 4 of 6 tests. `ArenaStore.recover()` prepares an update of `ended_at`, absent from its schema; even recovery on an empty in-memory database throws. `Arena` calls this at construction. The idempotence test also fails on negative zero. More substantively, `finishMatch()` calls `applyRating(current)` instead of the completed summary: a running match's null winner is treated as a draw. These are existing defects, left unchanged.
- Git has **no commits**, and all source files are untracked. Existing source, configuration, skill, dependency, and asset files were preserved. Build outputs were regenerated by the existing checks. No commits, installs, database migrations, public battles, browser battles, or deployment were performed.

The local simulator is independently usable despite the arena failures. Consequently, the only executable addition is `scripts/benchmark-gen6.mjs`. It uses the pinned upstream random agent rather than introducing an untested action mapper or learner. The repository's live-play skill is outside this task's scope.

## Measured laptop capacity

Hardware reports Apple M5 MacBook Pro, 10 CPU cores (4 performance / 6 efficiency), 10 GPU cores, 16 GB unified memory, macOS 26.5.1, and about 764 GiB available disk space. Metal is supported; a working PyTorch MPS installation has **not** been verified.

Run from the project root:

```sh
node scripts/benchmark-gen6.mjs 2000
```

The script runs only local Gen 6 Random Battles, one at a time. Both agents use upstream `RandomPlayerAI` with `move=0.8`, `mega=0.5`. It seeds battle randomness, both team generators, and both policies independently. Two identical-seed warmup games must have identical result statistics and spectator-log hashes (timestamps excluded). Warmups are excluded from throughput. Player inputs come only from their respective streams. Unused streams are drained, games are capped at 400 turns, caps are reported separately from genuine draws, and unexpected choice errors fail the run. Unavailable-choice responses are retried using the simulator's corrected request.

**Compute estimate, not measured training performance:** plan initially for 100–1,000 learner decisions/second after encoding, batched inference, interprocess transport, and PPO updates. This is a deliberately broad allowance below the measured simulator ceiling; slow per-action Python/MPS calls could be worse. When only one side learns, roughly half the simulator choices are learner samples. With both sides learning, both count, although they are correlated.

These are arithmetic budgets, not promises of convergence or competitive play. A million decisions corresponds to roughly 11,000 games when collecting both sides at this benchmark's game length, or 22,000 when collecting one. Learned policies may produce much longer games. The 27-second run is not a thermal/endurance test. Measure the real pipeline for ten minutes before scheduling long work; nothing is scheduled by this assessment.

Start with one persistent simulator worker and CPU inference; test 2–4 workers only after profiling. Target a total process footprint below 6 GB, leaving room for macOS and ordinary apps. Four workers at the observed footprint would consume roughly 2 GB before the learner and buffers, but scaling has not been measured. GPU and CPU share the same 16 GB. A 0.1–0.5 million parameter float32 model uses 0.4–2 MB of weights and roughly 1.6–8 MB for weights, gradients, and Adam moments, excluding activations and framework overhead. Rollouts and process overhead matter more than model weights here. Keep checkpoints and summaries; do not save every full battle audit.

## Smallest viable learning prototype

**Architecture:** persistent Node simulator → player-specific observation state → compact tensors and legal-action mask → small PyTorch policy/value network → request-indexed action → simulator. One persistent Python learner coordinates requests over JSON lines initially. Batch requests across environments, attach environment/episode/request IDs, and never expose the other player's pending choice. No HTTP server or browser is required. The official [simulator API](https://github.com/smogon/pokemon-showdown/blob/master/sim/SIMULATOR.md) supports direct streams and subprocess communication; the installed source is the authority for this pinned engine.

**Observation:** maintain a public-information state tracker separately for each player. Encode our six Pokémon's species/form, level, HP, status, stats, moves/PP, item, and ability from our requests; opposing Pokémon only as revealed by that player's protocol stream. Include boosts, active identities, revealed moves/items/abilities, weather, hazards, screens, terrain, Trick Room, and remaining side resources. Represent unrevealed opponents and unknown attributes with explicit unknown/presence indicators; a fainted Pokémon is not an unknown Pokémon. Opponent HP is the visible rounded value, not engine HP. Seeds, generated opposing sets, simulator internals, and omniscient audit fields never enter either policy or value input. Handle Illusion, form changes, temporary typing, and request-slot reorderings explicitly rather than treating displayed names as immutable identity.

**Network:** share small categorical embeddings and a small encoder across Pokémon slots; pool team summaries, retain active and candidate-action features, and feed a 128-unit trunk. Use a shared candidate-action scorer for the policy and a scalar value head. Budget 0.1–0.5M parameters after selecting vocabularies/features. Move features include Gen 6 type/category, power, accuracy, PP, priority and effects; candidate switches include their known state and matchup features. Query `Dex.mod('gen6')`, not current-generation move exports. Begin feed-forward with the explicit state tracker. Add a 128-unit GRU only if remembered event order or uncertainty becomes a demonstrated limitation. No tokenizer, language pretraining, transformer, or general-purpose LLM training is needed.

**Actions:** a fixed 14-slot mask: four normal moves, four corresponding Mega moves, and six switch targets. The active switch slot is masked, so not all 14 are simultaneously legal. `canMegaEvo` controls the Mega variants. Forced switches expose only eligible replacements; trapped states suppress voluntary switches; wait messages produce no transition; Struggle/locked-move requests use the simulator's actual request representation. Gen 6 has no Z-Moves, Dynamax, or Tera. Validate legality from requests, never hidden battle state. A previously unknown trap can reject a switch and reveal a corrected request: replace the pending rejected decision, do not reward it or advance the rollout as if a turn occurred. Preserve any information revealed in the correction. See the [protocol documentation](https://github.com/smogon/pokemon-showdown/blob/master/sim/SIM-PROTOCOL.md); regression-test against the installed implementation.

**Learning:** first train against a frozen attack-oriented random baseline; also implement a genuine expected-power/type/accuracy baseline with sensible forced switches. Mask logits before sampling and log-probability calculation. Use terminal win/loss/draw rewards of +1/−1/0, a learned value baseline, and [PPO](https://arxiv.org/abs/1707.06347) with GAE. Initial tuning defaults: gamma 0.99, lambda 0.95, clip 0.2, learning rate 3e-4, entropy coefficient 0.01, gradient norm cap 0.5, 2,048 decisions per rollout, minibatches of 256, four update epochs. These are starting settings, not validated hyperparameters. Bootstrap at rollout/time-limit truncation, never across an actual terminal boundary. Exclude simulator failures from game results. Avoid HP reward shaping initially: it can reward damage/healing loops and requires careful treatment of hidden information.

Store observation, mask, action, old log-probability, value, reward, terminal/truncation flags, and episode identity for each learner decision. Forced switches are decisions even without a new turn number. Freeze policy weights during a rollout. If imitation warmup is used, keep it a separate supervised stage; heuristic actions are not on-policy PPO samples. Later add frozen past checkpoints to the opponent pool and train both sides, resetting recurrent state per episode if recurrence is introduced.

**Success gate:** finite losses and real parameter changes are necessary but insufficient. Evaluate frozen checkpoints on held-out team/battle seeds, both seats, against random and the genuine heuristic; report wins/draws/losses, confidence intervals, cap/error rates, and decision throughput. Pre-generate two teams and explicitly swap them for paired evaluation; swapping player labels alone does not ensure this. Keep seeds and private teams in the evaluator, outside agent inputs. Use roughly 500–1,000 seed pairs and several training seeds before claiming an improvement. Bootstrap confidence intervals by pair because paired outcomes are correlated. Local baseline results are not public-ladder Elo.

## Dependencies, risks, and next steps

The benchmark adds **zero dependencies**. The proposed learner needs an isolated Python environment with compatible pinned PyTorch and NumPy versions; confirm wheels for this Python 3.14 installation or use a separate supported Python version without replacing the system interpreter. Prefer CPU first. PyTorch provides an [MPS backend](https://docs.pytorch.org/docs/stable/notes/mps.html), but check `torch.backends.mps.is_available()` and benchmark CPU against batched MPS on this actual machine before selecting it. Do not install CUDA packages.

Gymnasium is optional for a standardized adapter. Stable-Baselines3 plus sb3-contrib MaskablePPO is an alternative to a small custom PPO loop, at the cost of more dependencies and an environment adapter. poke-env offers an [existing masked RL example](https://poke-env.readthedocs.io/en/latest/examples/reinforcement_learning.html), but would add a local server/WebSocket path where direct streams already work. Its [documentation](https://poke-env.readthedocs.io/en/stable/index.html) also cautions that earlier-generation coverage may have gaps. Do not layer both approaches together for the first prototype.

The main risks are observation leakage, incomplete public-state parsing, Gen 6 mechanics mismatches, invalid/retried actions, terminal versus truncation bookkeeping, slot-identity errors, self-play overfitting, weak baselines, and uncertain sample efficiency. A small model fits; demonstrating strategy under hidden information is the harder part. Simulator pinning provides reproducibility but does not guarantee equivalence to a future public server's format data. The random-agent benchmark exercises Mega moves and switching, but does not prove a future encoder or mask correct.

Proceed in this order:

1. Repair and test arena recovery and completed-result rating application before using the arena for evaluation. Keep these fixes separate from the RL addition. The isolated training path need not depend on the arena database.
2. Add a Gen 6-only observation/action adapter outside the existing Gen 9 contract. Test forced switches, Struggle, Mega eligibility/consumption, disabled moves, hidden-trap retries, side redaction, and deterministic resets with independent seeds. Require two states differing only in hidden opponent information to encode identically until something is revealed.
3. Add the small masked policy/value model and persistent learner bridge in an isolated environment. Run a bounded 100k-decision pipeline check and measure end-to-end throughput and peak memory. Do not begin an overnight run based solely on this simulator benchmark.
4. Run a 1M-decision learning experiment, compare frozen checkpoints on held-out local seeds, then decide whether 10M decisions, recurrence, or checkpoint self-play is justified.

No trained agent or measured learning improvement is delivered by this assessment. The reproducible local benchmark and this design are the completed first step; integration and training remain gated by the concrete work above.
